# MKortex Updater — план

Один плагин-ядро: смотрит на свой GitHub-репозиторий, читает каталог экосистемы, предлагает установку и обновления. Защита «только для клиентов» — потом.

## 1. Идея

1. Всё в **одной монорепе**: исходники плагинов (не обязаны быть публичными по смыслу продукта) и папка с **готовыми билдами**.
2. В корне лежит `ecosystem.json` — список плагинов, версии, пути к билдам.
3. При открытии Obsidian updater скачивает каталог, сравнивает с локальным, предлагает обновить себя или другие плагины, умеет поставить отсутствующий.

Без ключей, без бэкенда на старте.

## 2. Монорепа и раздача

Исходники отдавать не нужно → одна репа удобнее: общий релизный процесс, один каталог, одни URL.

Obsidian не умеет «один плагин = вся экосистема». Ему нужны отдельные папки:

`.obsidian/plugins/<id>/main.js` + `manifest.json` (+ `styles.css`).

Поэтому «слить в один» = **один дистрибутив с несколькими папками**, не один `main.js`.

Структура билдов в репо — как в Obsidian:

```text
dist/
  mkortex-updater/
    main.js
    manifest.json
    styles.css
  mkortex-example/
    main.js
    manifest.json
    styles.css
ecosystem.json
```

Кто скачает весь `dist/` (или zip релиза) и скопирует содержимое в `.obsidian/plugins/` — получит все плагины сразу. Для текущего этапа это ок и даже удобно (ручная полная установка / бэкап экосистемы). Updater при этом может ставить **по одной папке**, читая версии из каталога.

В `dist/` не класть `data.json` — это настройки пользователя.

Рядом на диске (`audio-field-recorder`, `notion-like-editor`, …) можно постепенно переносить/собирать сюда; в экосистему попадает только то, что лежит в `dist/` и перечислено в `ecosystem.json`.

## 3. Что в каталоге

На каждый плагин:

- `id` — имя папки, совпадает с `manifest.id`
- `name` — имя в UI
- `version` — semver (как в manifest билда)
- `path` — путь в репо, например `dist/mkortex-updater`
- `minAppVersion` — совместимость с Obsidian
- `description` — коротко
- `changelog` или `releaseNotesUrl` — по желанию

В корне: `schemaVersion`. Updater — обычная запись в списке.

## 4. Откуда качать

Не отдельные репо и не GitHub API. Прямые raw/release URL на файлы в `dist/<id>/`:

`https://raw.githubusercontent.com/<org>/<repo>/<ref>/dist/<id>/main.js`  
(и то же для `manifest.json`, `styles.css`)

Либо один zip-ассет релиза на плагин / на весь `dist/` — как проще сделать CI. Для MVP достаточно трёх файлов по raw из `main`.

## 5. Поведение (UX)

Проверки: при старте Obsidian (с задержкой); кнопка в настройках. Без Command Palette, без таймера.

Обновления: notice/модалка; всё или по одному; после установки — automatic reload plugins.

Нет плагина: в настройках «не установлен» → Install.

Нет сети: тихий fail, установленное не трогать. Обновления только с согласия. Ничего не удалять из‑за каталога/доступа.

## 6. Сравнение версий

Локальный `manifest.json` vs `version` в каталоге.

- нет локально → установить
- каталог новее → обновить
- локально новее → не даунгрейдить

## 7. Установка в vault

1. Скачать файлы из `dist/<id>/` (или unzip папки).
2. Записать в `.obsidian/plugins/<id>/`.
3. Не затирать `data.json`.
4. Включить плагин (API или подсказка вручную).
5. Reload plugins.

`dependsOn` — не в MVP.

## 8. Как выпускать

1. Собрать плагин(и) в `dist/<id>/`.
2. Обновить `version` в `ecosystem.json` (и в manifest билда — одно и то же число).
3. Закоммитить / сделать release.
4. Клиенты при проверке видят апдейт.

Каталог — источник правды для клиентов. Версии независимы по плагинам: можно обновить только sync, не трогая updater (в `dist/` меняется одна папка).

Опционально позже: zip «вся экосистема» для первой ручной установки одним архивом; updater всё равно работает поштучно.

## 9. Важные детали

1. Первый раз updater — вручную (одна папка или zip). Дальше — через него.
2. Публичный `dist/` = любой может поставить всё копированием. Сейчас принимаем.
3. Кэш каталога; офлайн не ломает локальное.
4. Без GitHub API — только raw/файлы.
5. Писать обновление осторожно (временные файлы → замена).
6. `id` не переименовывать после выдачи.
7. Обновляется только текущий vault.
8. Пока desktop.
9. Задел: настройка URL каталога → потом бэкенд, тот же JSON.

## 10. Защита — потом

Публичный каталог и `dist/`. Позже — бэкенд вместо raw; без доступа нет install/update; установленное не удаляется.

## 11. Этапы

Этап 0: ✅ монорепа, `dist/`, `ecosystem.json`, каркас updater’а.

Этап 1 — MVP (в работе/готово локально): каталог; список в настройках; install/update; себя; старт-проверка; кэш; сохранить `data.json`.

Этап 2: changelog; аккуратная установка; `dependsOn`; URL каталога → бэкенд.

Этап 3: ключи/подписка; без wipe.

## 12. Риски

Всё из `dist/` можно скачать целиком. Ошибка в `ecosystem.json` на `main` бьёт всех. GitHub down — нет проверки обновлений.

## 13. Зафиксировано

- Одна монорепа; раздача — папки билдов как в Obsidian (`dist/<id>/`).
- Каталог и версии — `ecosystem.json` в этой же репе.
- Updater ставит/обновляет поштучно; полный `dist/` = ручной «поставить всё».
- Auth отложен; без доступа ничего не удаляем; апдейты только с согласия.
